# Datasets — status and requirements

## CURRENT STATUS: NO REAL-WORLD LABELED EMAIL DATASET EXISTS IN THIS REPOSITORY

**This must be stated plainly:** ForentisAI currently contains **no real
labeled email dataset**. Consequently:

- No real-world accuracy, precision, recall, F1, or AUC figure exists, and
  none may be claimed.
- The technical model is the **pipeline-validation fixture**
  (`ai/models/technical_model_fixture.joblib`), trained on a small
  synthetic dataset generated by `ai/training/generate_technical_fixture.py`.
  Its holdout accuracy is a **mechanical pipeline check only** — it is not
  a detection-performance number and must never be quoted as one.
- The NLP component now ships with the **official fine-tuned ForentisAI
  DeBERTa-v3 email-threat classifier**
  (`ai/models/nlp/forentisai_deberta_v3`, 184,423,682 parameters, trained
  from `microsoft/deberta-v3-base`). It was trained on
  **`ForentisAI_DeBERTa_Dataset_V2`, which is a synthetic dataset**. Its
  held-out V2 test metrics — accuracy/precision/recall/F1/ROC-AUC = 1.000
  over 4,499 samples — are **synthetic-dataset metrics only** and do NOT
  establish real-world deployment performance. **Independent evaluation on
  real emails is still required.**
- The base `microsoft/deberta-v3-base` model itself is **not** a phishing
  classifier; the inference layer refuses to predict with any artifact that
  lacks the official `forentisai_model.json` manifest
  (`"forentisai_model": true`,
  `"model_type": "deberta_v3_email_threat_classifier"`)
  — see `app/ai/nlp/model.py`.

## What production training requires

A legitimate dataset must be supplied by the project with:

1. **Source documentation** — where the emails came from, licensing/legal
   basis for use, and any preprocessing applied.
2. **Labeling methodology** — who labeled, with what guidelines, and the
   measured inter-annotator agreement.
3. **Class balance and volume** — enough examples of both classes; the
   exact minimum depends on the model and desired performance.
4. **No email PII leakage** — datasets must be handled per the project's
   privacy rules; raw mailboxes must never be committed to this repository.

## Raw-EML dataset preparation (Phase 1, offline)

`ai/training/prepare_dataset.py` converts a directory of raw `.eml` files
into a split, leakage-safe training dataset for the future technical model:

```bash
python ../ai/training/prepare_dataset.py \
    --input-dir <dataset_root>/benign,+malicious \
    --output-dir ../ai/datasets/processed/<name> \
    [--seed 42] [--source-dataset <name>]
```

- Labels: `benign/` → `benign`; `malicious/` → `suspicious` (the folder name
  `malicious` is never used as a model label).
- Each row carries **exactly 30 features** projected from the production
  extractors (10 `text.*`, 10 `header.*`, 8 `url.*`, 2 Received-chain IP
  counts). The runtime 48-feature evidence schema is untouched; the other 18
  runtime features (`auth.*`, DNS/RDAP/GeoIP intelligence) are NOT trained on
  in this phase.
- Strictly offline: Step 4 runs with `perform_dns=False`,
  `perform_rdap=False`, no GeoIP; no URLs are opened; Rspamd is not called.
- Leakage prevention: SHA-256 exact-duplicate removal, plus a conservative
  structural signature (`structural_sig_v1`: URLs→`<url>`, addresses→
  `<addr>`, dates→`<date>`, numbers→`<num>`, whitespace collapsed; wording
  preserved) grouping near-duplicates. A group never spans two splits.
- Split: seeded (default 42), stratified by label, 70/15/15 by rows.
- Outputs 8 files: 4 JSONL splits, statistics CSV, quality report (explicit
  PASS/FAIL), manifest YAML, and a README with usage and honesty notes.
- Malformed emails are recorded as failures in the quality report and
  excluded — never silently converted into training rows.

## Formats

### Technical model (classical ML)

JSON file:

```json
{
  "rows": [
    {"features": {"text": {...}, "header": {...}, "auth": {...}, "url": {...}, "intelligence": {...}}, "label": "benign"},
    {"features": {...}, "label": "suspicious"}
  ]
}
```

Feature objects must match the 48-name contract exported by
`app.schemas.features.feature_names()` (the training script validates this).

The fixture generator (`ai/training/generate_technical_fixture.py`) shows
the exact row shape.

### Transformer (DeBERTa-v3)

JSON file:

```json
{
  "rows": [
    {"text": "Subject and body text of one email...", "label": "benign"},
    {"text": "...", "label": "suspicious"}
  ]
}
```

Labels are exactly `benign` / `suspicious`.

## Training commands (from `backend/`, venv active)

```bash
# Technical model — pipeline validation fixture (NOT a production model):
python ../ai/training/generate_technical_fixture.py
python ../ai/training/train_technical_model.py --use-fixture

# Technical model — real dataset (default mode; refuses without one):
python ../ai/training/train_technical_model.py --dataset ../ai/datasets/external/<your_dataset>.json

# Transformer — requires a real labeled dataset (no fixture mode by design):
python ../ai/training/train_transformer.py --dataset ../ai/datasets/external/<your_labeled_text>.json
```

Artifacts land in `ai/models/` (git-ignored). Inference picks them up via
`AI_MODEL_DIR` / `TECHNICAL_MODEL_PATH` / `NLP_MODEL_PATH`.
